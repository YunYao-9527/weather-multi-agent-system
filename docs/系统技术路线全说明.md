# 强对流预警多智能体辅助决策系统技术路线全说明

本文档用于完整解释当前系统的技术路线、核心思路、主要名词、模块边界、算法逻辑、治理机制、接口设计、回放审计机制，以及这些设计为什么这样做。它不是一份“宣传稿”，而是一份给研发、评估、运维、申报材料、系统交底都能直接使用的工程说明。

## 1. 系统一句话定义

这是一个面向强对流预警辅助决策的多智能体系统。  
它不是官方自动发布系统，而是一个“对象化、保守型、可审计、可回放、可评估、可演进”的业务辅助技术底座。

系统的核心原则是：

- 宁可保守，不误发。
- 宁可转人工，不自动冒进。
- proxy 数据可以用于实验参考，但不能污染正式评估、正式演进和正式动作建议链路。
- 多个同源证据不能重复抬高概率。
- 单帧高分不能直接触发对象级动作建议。

## 2. 为什么系统要这样升级

原始研究型原型通常有几个问题：

- 输入是单点 Observation，无法承载全国业务场景中“格点、区域、对象、事件”的语义。
- 多个 Agent 虽然都在推理，但常常依赖同一批上游信息，容易出现“看起来很多票，其实是同源重复”的问题。
- 如果数据源中混入 proxy 或代理数据，而系统没有正式治理边界，就会导致正式评估和正式建议失真。
- 如果系统只保存最终概率，不保存中间证据、策略快照、版本信息、回放包，就很难回答“为什么给出这个建议”“谁该为这个结果负责”。
- 如果动作建议只由单次概率触发，就会在短时噪声、抖动、源失稳时频繁误触发。

因此，当前系统把技术路线升级为：

`标准化数据平面 -> ObservationEnvelope -> 多 Agent 证据生成 -> family-aware fusion -> HazardObject 引擎 -> Policy Engine -> DecisionPacket -> Audit / Replay / Eval / Evolve`

## 3. 整条主链路怎么跑

端到端流程如下：

1. 数据层通过 Provider 抽象接入模式、雷达、客观指导等源。
2. 各 Provider 输出统一元数据和标准化 payload，并做 validate / fingerprint / health_status。
3. 原始输入被整理成 ObservationEnvelope，而不是直接让 Agent 吃散乱字段。
4. 8 个 Agent 分别从环流、环境、雷达、短临、客观指导、模式一致性、质量守卫、跨源一致性等角度生成 EvidenceCard。
5. 融合层先做 evidence family 聚合，再做跨 family 保守融合，生成 hazard_prob_raw、hazard_prob、calibrated_prob、lower_confidence_bound、p_release。
6. 对象引擎根据融合结果和时空上下文生成或更新 HazardObject，维护对象生命周期、持续性、面积、运动稳定性和对象版本。
7. Policy Engine 读取激活中的 PolicySnapshot，对对象和融合结果执行保守型闸门判断，输出 DecisionPacket。
8. Orchestrator 把推理输入、证据、融合快照、策略快照、决策轨迹、lineage、版本引用打成 ReplayBundle，并写入审计和快照存储。
9. 评估体系用 TruthFactory 生成 truth_version，并通过 Eval Manifest 绑定 code/model/policy/truth/calibration 等版本，对结果做正式评估。

## 4. 系统中的核心对象都是什么

### 4.1 Observation

Observation 是系统的旧输入模型。  
它适合单次样本推理，字段主要是：

- 环境量，如 CAPE、DCAPE、垂直速度、低层辐合、湿度、切变。
- 雷达量，如最大反射率、弓形回波、风暴运动速度。
- 客观概率指导，如短时强降水、大风、冰雹、龙卷概率。
- source_meta，用于带一些上游信息。

它的问题是：

- 语义是“一个样本”，不是“一个时空包络”。
- 它不能稳定描述数据来源、网格、覆盖范围、质量诊断、对象上下文。
- 不能很好支撑国家级业务中的对象化判定和多源治理。

所以 Observation 现在被保留为兼容层，而新版核心输入已经切到 ObservationEnvelope。

### 4.2 ObservationEnvelope

ObservationEnvelope 是新版统一输入合同。  
可以把它理解成“一个时刻、一个业务域、一个标准化证据包”。

它的关键字段有：

- `envelope_id`：本次标准化输入包的唯一标识。
- `analysis_time`：分析时刻。
- `valid_time`：本次输入对应的有效时刻。
- `lead_time`：时效。
- `domain_id`：业务域标识，比如城市域、区域域。
- `grid_spec`：网格规格，定义空间参考系和网格参数。
- `feature_planes`：标准化后的特征平面。
- `source_registry`：本次输入涉及的 ProviderRecord 列表。
- `qc_registry`：每个数据源的 QCRecord。
- `provenance_manifest`：字段级来源清单。
- `object_context`：对象相关上下文，如运动方向、对象坐标。
- `source_tiers_summary`：official / experimental / proxy 汇总。

为什么要做这个结构：

- 让 Agent 的输入不再和某个具体数据源强绑定。
- 让融合、策略、回放、审计都能拿到统一的元数据。
- 让旧 Observation 也能通过 adapter 自动转成新版输入，不破坏兼容性。

### 4.3 ProviderRecord

ProviderRecord 是一次数据接入实例的标准元数据。

主要字段：

- `source_id`：具体数据源编号。
- `source_family`：数据家族，比如 radar、guidance。
- `source_tier`：official / experimental / proxy。
- `provider_version`：Provider 自己的版本。
- `issue_time` / `valid_time` / `ingest_time`：签发、有效、入库时间。
- `latency_sec` / `freshness_sec`：延迟和新鲜度。
- `coverage`：空间覆盖情况。
- `qc_flags`：质量标志。
- `fingerprint`：本次数据快照指纹。
- `data_snapshot_id`：快照引用。

为什么要有它：

- 国家级业务辅助系统里，数据“从哪来”不能只靠注释说明。
- 需要明确区分正式源、实验源、代理源。
- 需要在回放时能准确找到“当时使用的是哪份源数据”。

### 4.4 QCRecord

QCRecord 是对单个输入源做质量诊断后的结果。

主要内容：

- 是否 stale。
- 是否 missing。
- 空间覆盖是否正常。
- 时间对齐是否正常。
- 版本是否已注册。
- 质量 flags。

为什么要有它：

- 如果关键源 stale 或 coverage 异常，系统不能静默继续。
- 质量问题必须进入 veto 或 degraded mode，而不是只在日志里留一行。

### 4.5 EvidenceCard

EvidenceCard 是单个 Agent 输出的一张证据卡片。

它不是“一个最终结论”，而是“一个 Agent 对某类危险天气的局部判断”。

字段包括：

- `agent`：证据来自哪个 Agent。
- `claim`：这个 Agent 的判断结论。
- `confidence`：这个判断自己的置信度。
- `hazard_scores`：对各灾种的分 hazard 分值。
- `supporting_features`：支撑结论的关键特征。
- `freshness_seconds`：证据时效。
- `proxy_source`：是否主要依赖 proxy。
- `upstream_sources`：上游数据源。
- `rule_version` / `model_version`：规则或模型版本。
- `family`：证据家族。
- `source_tier`：证据最终对应的数据等级。
- `provider_fingerprint`：所依赖数据快照指纹。

为什么要做成卡片：

- 便于保留“每个 Agent 到底看到了什么、说了什么、为什么这么说”。
- 便于后续做 per-agent contribution 和 family contribution。
- 便于审计与回放。

### 4.6 FusionResult

FusionResult 是融合层的输出。  
它不是一个单独概率，而是一组经过治理后的概率与诊断结果。

关键字段：

- `hazard_prob_raw`：未经质量折减的原始融合概率。
- `probability_quality_factor`：概率质量因子。
- `hazard_prob`：折减后的危险天气概率。
- `calibrated_prob`：经过校准器处理后的概率。
- `lower_confidence_bound`：保守下界。
- `p_release`：真正用于动作判定的保守释放概率。
- `per_agent_contribution`：每个 Agent 的贡献。
- `family_contribution`：每个证据家族的贡献。
- `conflicts`：冲突项。
- `proxy_dependency_ratio`：proxy 依赖占比。
- `effective_source_tier`：当前有效证据中的最高等级。
- `veto_reasons`：融合层已经发现的 veto 原因。
- `degraded_mode_flags`：降级标志。
- `evidence_readiness_score`：证据就绪度。

为什么不是只保留一个 hazard_prob：

- 原始概率太乐观，不能直接用于高风险动作建议。
- 系统需要区分“证据强不强”和“当前是否适合放行动作”。
- 融合结果不仅要给概率，还要给解释、冲突、降级、源等级、质量状态。

### 4.7 HazardObject

HazardObject 是系统对象化后的核心业务对象。

可以把它理解成：

“系统当前识别并持续跟踪的一个危险天气对象”。

字段包括：

- `object_id`：对象标识。
- `parent_object_id`：父对象标识。
- `object_type`：对象类型。
- `hazard_type`：灾种。
- `geometry`：对象几何。
- `centroid`：质心。
- `area_km2`：面积。
- `motion_vector`：运动矢量。
- `lifecycle_state`：生命周期状态。
- `start_time` / `end_time` / `last_update_time`：起止和更新时刻。
- `confidence`：当前对象置信度。
- `support_evidence_ids`：支撑证据。
- `source_tiers`：所依赖的数据层级。
- `object_version`：对象版本号。
- `evidence_persistence`：证据持续性。
- `source_stability`：源稳定性。
- `motion_stability`：运动稳定性。

为什么一定要引入对象：

- 实际业务动作针对的是“对象”或“区域”，不是一个孤立样本。
- 只有对象才能承载持续时间、面积、运动、合并分裂、历史版本这些业务语义。
- 对象化之后，issue / clear 才能变成生命周期问题，而不是单帧阈值问题。

### 4.8 PolicySnapshot

PolicySnapshot 是版本化的策略快照。

它把动作建议规则从代码里解耦出来，变成可注册、可激活、可审计的治理资产。

关键字段：

- `policy_version`
- `issue_threshold`
- `clear_threshold`
- `lower_bound_threshold`
- `min_duration`
- `min_area`
- `max_proxy_share`
- `required_independent_families`
- `stale_source_rules`
- `conflict_veto_rules`
- `quality_veto_rules`
- `manual_review_rules`
- `hold_down_rules`
- `coverage_rules`

为什么要版本化：

- 同样一套输入，用不同政策会得出不同动作。
- 如果不保存 policy version，就无法解释“为什么这次建议 issue，上次却 manual_review”。
- 正式评估、正式演进、正式动作建议都必须绑定策略版本。

### 4.9 DecisionPacket

DecisionPacket 是策略层的正式输出。

它不是 UI 文案，而是系统的标准动作建议包。

字段包括：

- `action`：动作，如 recommend_issue、recommend_clear、manual_review。
- `level`：等级。
- `rationale`：解释理由。
- `veto_triggered` / `veto_reasons`
- `policy_version`
- `object_id`
- `recommended_by`
- `requires_human_review`
- `effective_probability_used`
- `issue_gate_passed`
- `clear_gate_passed`

为什么单独做一个包：

- 让动作层从融合层独立出来。
- 动作结果必须能回答“用了哪个 policy、对哪个对象、由哪些 family 支持、为什么被 veto”。

### 4.10 ReplayBundle

ReplayBundle 是一次完整推理周期的可重放封装。

至少包括：

- source snapshot references
- normalized features
- agent outputs
- fusion snapshot
- policy snapshot
- decision trace
- code reference
- model references
- truth reference
- lineage

为什么它这么重要：

- 审计的关键不是“我把最终 JSON 存下来了”，而是“我能不能用同一套输入和版本，把当时的结果稳定重现出来”。
- 没有 ReplayBundle，就没有真正的可追责和可归因。

## 5. 数据平面是怎么做的

### 5.1 什么是数据平面

数据平面可以理解为：

“系统如何接入、标准化、标记、验证和治理外部数据源的那一层能力”。

当前系统的数据平面通过 Provider 抽象完成。

### 5.2 Provider 抽象怎么设计

每个 Provider 都要实现这些标准方法：

- `fetch()`：拉取原始数据。
- `normalize()`：归一化到统一合同。
- `validate()`：做质量检查，输出 QCRecord。
- `fingerprint()`：为当前数据快照生成稳定指纹。
- `health_status()`：输出源健康状态。

这样设计的好处：

- 任何新数据源接进来，都必须走统一接口。
- 正式源、实验源、代理源都能在同一治理框架里比较。
- 外部正式数据即使暂时还没接入，系统也已经具备标准接入位。

### 5.3 source_tier 是什么

`source_tier` 是数据源等级，用来强制区分数据在正式链路中的身份。

分三类：

- `official`：正式业务源。
- `experimental`：实验源或正式候选源。
- `proxy`：代理源、兜底源、特征工程近似源。

为什么必须严格区分：

- proxy 可以帮助系统“不断点”，但它不能伪装成正式能力。
- headline 指标、policy activation、正式动作建议不能被 proxy 混入。

### 5.4 当前接入的数据源如何分层

当前系统里的典型映射：

- Open-Meteo guidance：`experimental`
- Local radar grid：`experimental`，但标记 `official_candidate`
- NowCoast radar：`experimental`，也保留 `official_candidate` 语义
- RainViewer radar fallback：`proxy`
- 客观概率代理：`proxy`

这里的设计重点不是“谁更强”，而是“谁能进入正式链路”。

### 5.5 stale 检测和 source health 怎么做

系统会对每个 Provider 做这些检查：

- freshness 是否超阈值。
- coverage 是否过低。
- provider_version 是否存在。
- qc_flags 是否包含 fetch_failed、stale、coverage_low 等异常。

这些结果会进入：

- `qc_registry`
- `source_health_summary`
- `fusion.veto_reasons`
- `degraded_mode_flags`
- `policy_engine`

所以关键源 stale 不是“打个 warning 就算了”，而是会影响最终动作建议。

## 6. 多 Agent 协同层是怎么做的

### 6.1 系统里有哪些 Agent

当前系统是 8 个 Agent：

- circulation
- environment
- objective_guidance
- model_consensus
- radar
- nowcast
- data_quality_guard
- cross_source_consistency

### 6.2 为什么不是一个大 Agent 干完

原因有三个：

- 不同证据家族的物理含义不一样，拆开更便于审计。
- 如果一个模块退化，不会直接把整个系统搞成黑盒。
- 后续评估、演进和治理必须知道“到底是哪一类证据出了问题”。

### 6.3 data_quality_guard 为什么被做成诊断型 Agent

它不负责抬高 hazard 分数，而是负责指出：

- 数据是否缺测。
- 数据是否 stale。
- 质量是否可疑。
- 当前是否该触发 degraded mode 或 manual review。

也就是说，它是“守门员”，不是“加分项”。

## 7. family-aware fusion 是怎么做的

### 7.1 什么是 evidence family

evidence family 是证据家族。  
它的目的是防止多个“看起来不同、实际上同源”的 Agent 重复抬高概率。

当前定义的家族包括：

- radar
- environment
- circulation
- objective_guidance
- model_guidance
- nowcast
- quality_control
- cross_consistency
- human_override

### 7.2 为什么不能直接按 Agent 投票

如果直接按 Agent 线性叠加，会出现一个问题：

- 雷达 Agent 和 nowcast Agent 很可能都主要依赖雷达。
- objective_guidance 和 model_consensus 也可能都建立在模式指导之上。

如果把它们当独立票数，系统就会虚高。

所以现在的逻辑是：

1. 先按 family 聚合。
2. family 内部做保守聚合，而不是简单求和。
3. 再做跨 family 融合。

### 7.3 同 family 内部怎么聚合

当前实现是取保守聚合：

- 先取 top 值。
- 再引入 median。
- 最后按 `0.8 * top + 0.2 * median` 组合。

这背后的思路是：

- 既保留最强信号。
- 又不让单条异常证据完全主导。

### 7.4 proxy 为什么会被单独惩罚

当前融合层会对 proxy 做几件事：

- 限制权重上限。
- 统计 proxy_dependency_ratio。
- 在 probability_quality_factor 中加入惩罚。
- 超过 policy 上限时直接进入 veto 或 manual_review。

这保证 proxy 只能作为补充，不会变成正式链路的主力。

### 7.5 hazard_prob_raw、hazard_prob、calibrated_prob、lower_confidence_bound、p_release 分别是什么

`hazard_prob_raw`
: 家族聚合之后、尚未经过质量折减的原始概率。

`hazard_prob`
: 原始概率乘上 probability_quality_factor 之后的折减概率。

`calibrated_prob`
: 经过校准器修正后的概率，用来改善可靠性。

`lower_confidence_bound`
: 给当前概率减去不确定性边际后的保守下界。

`p_release`
: 最终用于动作建议的保守释放概率，当前实现取 `min(calibrated_prob, lower_confidence_bound)`。

为什么动作不直接用 hazard_prob：

- 因为高风险业务里，“高估风险”成本和“低估风险”成本都很高，必须把不确定性显式引入动作层。
- `p_release` 的意义就是：即便当前概率看起来高，只要下界不稳，就不轻易放行动作。

### 7.6 evidence_readiness_score 是什么

它可以理解成“当前证据是否足够成熟，可以进入动作决策”的综合分。

它综合考虑：

- evidence_strength
- agreement_score
- data_quality_score
- freshness_score
- model_dispersion_score
- proxy_dependency_ratio

所以这个分数不是天气强度，而是“决策就绪度”。

## 8. Hazard Object 引擎是怎么做的

### 8.1 为什么要从样本级升级为对象级

样本级系统的典型问题是：

- 同一片对流回波在连续时刻会被当成多个独立样本。
- issue / clear 容易受短时抖动影响。
- 很难表达面积、移动方向、对象合并分裂。

对象引擎的目标就是把概率序列变成可持续跟踪的业务对象。

### 8.2 lifecycle_state 是什么

对象状态机当前至少包括：

- `candidate`
- `watch`
- `recommend_issue`
- `active`
- `recommend_clear`
- `cleared`
- `manual_review`

状态含义：

- `candidate`：刚出现，尚不稳定。
- `watch`：有持续信号，但还未满足正式建议条件。
- `recommend_issue`：满足保守 issue 条件，建议发。
- `active`：对象持续处于已建议或激活状态。
- `recommend_clear`：满足清除条件，建议 clear。
- `manual_review`：存在 veto 或关键信息不足，必须转人工。

### 8.3 persistence、min_duration、min_area 为什么重要

系统明确禁止单帧高分直接触发动作。

因此对象引擎会维护：

- `evidence_persistence`
- `min_duration_met`
- `min_area_met`
- `source_stability`
- `motion_stability`

它们共同回答一个问题：

“这个对象是不是一个足够稳定、足够持续、足够可信的业务对象，而不是一瞬间的噪声尖峰？”

### 8.4 merge / split 为什么是对象引擎要处理的

强对流对象在实际运行中会合并、分裂、偏移。  
如果不做对象级处理，就会导致：

- object_id 频繁跳变。
- 审计和历史追踪断裂。
- 回放时无法稳定复现对象轨迹。

当前实现已经预留了 merge/split 语义字段，并通过空间匹配和对象版本更新控制对象 ID 抖动。

## 9. Policy Engine 是怎么做的

### 9.1 为什么要把策略和代码解耦

因为系统里至少有三层逻辑：

- “证据层”关心天气是否有风险。
- “融合层”关心概率是否可信。
- “策略层”关心在当前业务制度下是否允许给出动作建议。

这三者不能混在一起，否则会变成不可解释的大打分器。

### 9.2 issue_gate 和 clear_gate 是什么

`issue_gate`
: 是否满足建议发布的保守条件。

它至少检查：

- p_release 是否达到 issue_threshold。
- lower_bound 是否达到 lower_bound_threshold。
- evidence_persistence 是否达到 min_duration。
- area_km2 是否达到 min_area。
- independent_family_count 是否足够。

`clear_gate`
: 是否满足建议清除的条件。

它会检查：

- p_release 是否低于 clear_threshold。
- lower_bound 是否也低于 clear_threshold。

### 9.3 veto 是什么

veto 就是硬闸门。  
一旦触发，动作不能自动放行，必须 manual_review。

当前典型 veto 条件包括：

- proxy 占比超限。
- independent family 数不足。
- min_area 未满足。
- min_duration 未满足。
- degraded_mode。
- 版本未注册。
- replay 校验失败。
- truth 链非法。

为什么要有 veto：

- 因为高风险系统里“没有足够把握”本身就是一个决策信号。
- 不能把所有不确定性都硬压成 issue 或 clear。

## 10. 真值工厂是怎么做的

### 10.1 TruthFactory 在解决什么问题

传统做法常把真值当成一个零散标签文件。  
但正式评估里需要回答：

- 这次评估绑定的是哪一版 truth？
- 真值来自 gold 还是 silver 还是 proxy？
- 真值是 point 级、grid 级、object 级还是 event 级？
- 这一版 truth 能不能被覆盖修改？

TruthFactory 就是为了解决这些治理问题。

### 10.2 四层 truth 是什么

系统支持四层 TruthRecord：

- `point truth`
- `grid truth`
- `object truth`
- `event truth`

它们分别回答：

- 站点有没有发生。
- 某网格有没有发生。
- 某对象有没有发生。
- 某次天气过程有没有发生。

为什么不能只做站点：

- 国家级业务能力不能只按站点命中统计。
- 系统的动作是对象化和区域化的，真值也必须能映射到 grid 或 object。

### 10.3 truth_version 是什么

truth_version 是一次正式真值快照的唯一版本号。

它是 append-only 的，也就是：

- 只能新增。
- 不能覆盖。

为什么必须这样：

- 否则今天跑出来的 headline 指标，明天可能因为“真值被覆盖了”而变得不可复现。

### 10.4 gold / silver / proxy 为什么不能混

分层意义：

- `gold`：正式 headline 可用。
- `silver`：可用于补充分析。
- `proxy`：只能用于实验参考。

当前系统明确要求：

- 正式 headline 指标只允许 gold。
- proxy truth 混入 headline 必须失败。

## 11. 评估体系是怎么做的

### 11.1 为什么不只做样本级准确率

因为这个系统不是一个单样本分类器。  
它至少要同时回答四类问题：

- 概率准不准。
- 事件打没打中。
- 空间对象对不对。
- 动作建议值不值得信任。

### 11.2 四层评估结构

当前设计的评估层次：

- 概率级评估
- 事件级评估
- 空间级评估
- 业务动作级评估

#### 概率级评估

主要看：

- Brier score
- reliability
- calibration curve
- ROC/AUC
- PR/AUPRC

#### 事件级评估

主要看：

- hit
- false alarm
- miss
- lead time
- duration error
- clear delay

#### 空间级评估

主要看：

- grid / object 匹配
- 预留 MODE / MTD 风格接口

#### 业务动作级评估

主要看：

- recommend_issue 准确性
- recommend_clear 稳定性
- manual_review 触发质量
- 非对称代价矩阵

### 11.3 Eval Manifest 是什么

Eval Manifest 是每次正式评估的绑定清单。

至少包括：

- `eval_manifest_id`
- `data_snapshot_id`
- `truth_version`
- `feature_version`
- `code_sha`
- `model_version`
- `calibration_version`
- `policy_version`
- `run_config_hash`

为什么它这么关键：

- 没有 manifest，就无法确认“这份成绩单到底是怎么跑出来的”。
- 评估结论必须绑定代码、特征、策略、真值和配置版本。

### 11.4 bootstrap CI 为什么要按事件日或区域块抽样

因为天气过程不是 iid 样本。  
如果简单按样本点自助抽样，会低估不确定性。

所以正式 headline 指标的 CI 应优先按：

- 事件日
- 过程日
- 区域块

做聚合抽样。

## 12. 审计与回放为什么是系统核心，而不是附属功能

### 12.1 六类 lineage 是什么

系统当前明确维护六类血缘：

- `source_lineage`
- `transform_lineage`
- `feature_lineage`
- `model_lineage`
- `policy_lineage`
- `human_lineage`

它们分别回答：

- 数据来自哪里。
- 中间经过了哪些变换。
- 用了哪版特征定义。
- 用了哪版模型或规则。
- 用了哪版策略。
- 是否经过人工干预或人工复核。

### 12.2 request_id、trace_id、run_id、bundle_id 分别是什么

`request_id`
: 一次 API 请求的标识。

`trace_id`
: 一条完整追踪链路的标识，通常与 request 关联。

`run_id`
: 一次推理周期的结果标识。

`bundle_id`
: 一次 ReplayBundle 的标识。

为什么要区分：

- request 关注入口。
- trace 关注链路。
- run 关注结果。
- bundle 关注回放资产。

### 12.3 replay determinism 是什么

它指的是：

“同一个 ReplayBundle，用同样的版本和容差重放，结果必须一致。”

当前系统会比较：

- hazard_prob 等数值输出。
- 是否在容差内一致。

这保证回放不是“差不多像”，而是真正可核验。

## 13. 存储架构是怎么做的

### 13.1 为什么不能继续全靠 SQLite + 零散 JSON

因为正式治理场景里有三类存储需求：

- 元数据与注册中心。
- 对象和几何相关资产。
- 大字段快照与回放包。

如果全部混在 SQLite 或散 JSON 里，会出现：

- 查询困难。
- 版本关系混乱。
- 审计检索成本高。

### 13.2 当前存储分层

当前系统已完成存储抽象，至少分为：

- 元数据/注册层：RegistryStore、ObjectStore 抽象。
- 对象层：ObjectRepository。
- 快照层：`runs/` 下的 replay bundles、truth snapshots、audit records、cycle snapshots。

已落地的目录语义包括：

- `runs/cycles`
- `runs/audit`
- `runs/replay_bundles`
- `runs/objects`
- `runs/truth_factory`
- `runs/registry`

未来如果外部条件允许，可以无缝挂接 PostgreSQL / PostGIS，而不需要推翻业务内核。

## 14. 接口层是怎么分的

### 14.1 为什么要按业务层次拆接口

因为系统不是一个单接口 demo。  
它至少有这些边界：

- 推理边界
- 数据接入边界
- 真值边界
- 治理边界
- 审计回放边界
- 空间对象边界

### 14.2 当前接口组

#### 推理层

- `/api/v1/infer/realtime`
- `/api/v1/infer/object`
- `/api/v1/infer/batch`

#### 数据层

- `/api/v1/ingest/providers`
- `/api/v1/ingest/health`
- `/api/v1/data/snapshots`

#### 真值层

- `/api/v1/truth/build`
- `/api/v1/truth/versions`
- `/api/v1/truth/validate`

#### 治理层

- `/api/v1/eval/run`
- `/api/v1/eval/report/{id}`
- `/api/v1/evolve/run`
- `/api/v1/policy/validate`
- `/api/v1/policy/activate`

#### 审计回放层

- `/api/v1/audit/trace/{request_id}`
- `/api/v1/replay/run`
- `/api/v1/replay/compare`
- `/api/v1/replay/bundles`
- `/api/v1/replay/compare-bundles`

#### 对象层

- `/api/v1/objects/active`

#### 注册中心

### 14.3 为什么统一 response schema

所有接口统一返回：

- `code`
- `message`
- `request_id`
- `trace_id`
- `data`

这样做的价值：

- 前端不用为每个接口写一套不同解析逻辑。
- request_id / trace_id 可以贯穿调试、审计、回放。

## 15. 前端为什么也要跟着重构

因为如果前端还只是展示一个最终概率，那后端再强，业务人员也看不出系统已经升级了什么。

现在前端已经接入这些新能力：

- 对象生命周期时间线
- family contribution 条形图
- replay bundle 对比
- truth version 对比
- provider health / registry / active objects 运维面板

这意味着系统对业务人员展示的已经不是“一个分数”，而是一条完整的业务解释链。

## 16. 这个系统里的“保守”具体体现在哪里

保守不是一句口号，而是具体落在多个层次：

### 16.1 数据层保守

- source_tier 分层。
- stale / coverage / missing 检测。
- proxy 不伪装成正式源。

### 16.2 融合层保守

- 同 family 不重复线性加权。
- proxy 权重上限。
- 冲突惩罚。
- p_release 使用概率下界。

### 16.3 对象层保守

- 单帧高分不直接 issue。
- 必须满足持续性和面积约束。
- 对象抖动要控制。

### 16.4 策略层保守

- veto 直接转 manual_review。
- 版本未注册不放行。
- replay 校验失败不放行。
- truth 链不合法不放行。

## 17. 演进和优化是怎么做的

系统的演进不是“在线自己乱改参数”，而是在治理边界下有约束地学习。

当前已有的演进机制包括：

- 基于 train 集 agent 误差学习权重。
- shrinkage 收缩，避免样本不足时权重过拟合。
- calibrator 支持 histogram / beta，并在样本不足时自动回退。
- baseline 与 enhanced 共享同一测试集。
- test 正例不足时可触发硬失败。

为什么要这样做：

- 强对流属于高波动、正负样本不平衡场景。
- 如果没有收缩、校准、时间切分和真值隔离，所谓“演进”很容易只是过拟合。

## 18. 测试体系是怎么做的

### 18.1 单元测试覆盖什么

已覆盖或要求覆盖：

- provider normalization
- policy engine
- family-aware fusion
- truth version isolation
- replay determinism

### 18.2 集成测试覆盖什么

至少覆盖：

`ingest -> observation_envelope -> agents -> fusion -> object -> decision -> audit -> replay`

### 18.3 安全闸门测试覆盖什么

必须验证这些场景会被拦住：

- stale source
- proxy 超限
- conflict 失控
- quality guard 异常
- truth 违规混入

这些场景不是“看 warning”，而是要么 manual_review，要么 hard fail。

## 19. 现在系统已经具备了什么，哪些还依赖正式数据接入

### 19.1 已具备的技术骨架

当前已经具备：

- 标准化 Provider 抽象层
- ObservationEnvelope 时空包络
- 8 Agent 协同推理
- family-aware fusion
- HazardObject 引擎
- Policy Engine
- TruthFactory
- Eval Manifest
- ReplayBundle
- Registry
- 前端运维与可视化

### 19.2 接口已就绪 / 数据待接入

以下能力的“技术接口已经准备好”，但要完全发挥国家级业务能力，仍需要正式数据接入：

- 正式模式指导产品 Provider
- 正式雷达拼图 / 雷达对象产品 Provider
- 正式客观概率产品
- 全国统一对象级 / 网格级正式真值
- PostgreSQL / PostGIS 级别的正式后端基础设施

这部分必须明确说明为：

“接口已就绪 / 数据待接入”

不能用实验源或 proxy 伪造正式能力。

## 21. 名词速查表

下面是系统里最常见名词的通俗解释。

`Provider`
: 数据接入适配器，负责 fetch、normalize、validate、fingerprint、health_status。

`source_family`
: 数据家族，比如 radar、guidance。

`source_tier`
: 数据等级，official / experimental / proxy。

`ObservationEnvelope`
: 标准化输入包，是 Agent 和融合层真正消费的统一合同。

`feature_planes`
: 标准化后的特征平面，按环境、雷达、指导等语义组织。

`EvidenceCard`
: 一个 Agent 的局部证据输出。

`family-aware fusion`
: 先按证据家族聚合，再跨家族融合的保守型融合逻辑。

`hazard_prob_raw`
: 未经过质量折减的原始融合概率。

`probability_quality_factor`
: 概率质量折减因子。

`hazard_prob`
: 折减后的概率。

`calibrated_prob`
: 校准后的概率。

`lower_confidence_bound`
: 保守下界。

`p_release`
: 真正用于动作放行的保守释放概率。

`HazardObject`
: 被系统持续跟踪的危险天气对象。

`lifecycle_state`
: 对象生命周期状态。

`PolicySnapshot`
: 策略快照，描述当前动作规则。

`DecisionPacket`
: 正式动作建议包。

`TruthFactory`
: 真值工厂，负责 ingest、normalize、reconcile、version、publish。

`truth_version`
: 一版不可覆盖的正式真值快照。

`Eval Manifest`
: 一次正式评估的绑定清单。

`ReplayBundle`
: 一次推理周期的可重放资产包。

`lineage`
: 血缘追踪信息。

`manual_review`
: 系统保守地把动作交还人工，不自动冒进。

`degraded_mode`
: 降级模式，表示系统还在运行，但可信度或完备性已经下降。

`veto`
: 硬闸门，表示自动动作不能放行。

## 22. 最后总结

这个系统不是在做一个“更复杂的打分器”，而是在搭一个业务辅助底座。

它的核心不是某一个 Agent，也不是某一个概率公式，而是下面这套技术骨架共同成立：

- 数据有分级、有健康诊断、有标准接入合同。
- 输入有统一时空包络，不再是散乱样本。
- 证据按家族保守融合，不让同源重复抬高。
- 决策围绕对象生命周期，而不是单帧高分。
- 动作建议通过版本化 policy 放行，而不是写死在业务代码里。
- 真值、评估、演进、审计、回放全部版本化绑定。
- proxy 不污染正式链路。
- 不满足条件就转人工。

如果要用一句更适合对外汇报的话来概括：

这套系统已经从“工程化研究原型”，升级成了“面向国家级业务辅助场景的对象化、保守型、可审计、可回放、可评估、可追责的技术底座”。
